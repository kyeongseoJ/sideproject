# 사용자 성향 분석 SDD

## 문서 정보

- 프로젝트: Novelty
- 기능: 사용자 성향 분석과 프로필
- 상태: 현재 구현 기준
- 운영 DB: Supabase PostgreSQL

## 목적

사용자가 어떤 환경과 행동 방식을 선호하는지 수집하고, 그 결과를 행동 선호 프로필로 저장한다. 이 결과는 의료 진단이 아니며 미션 추천과 프로필 표시를 위한 서비스 데이터다.

## 공식 흐름

```text
회원가입·로그인
→ X-User-Key 기반 사용자 복원
→ 여섯 문항 입력
→ POST /api/personality-analyses
→ 성향 분석·원본 답변·현재 프로필 저장
→ 프로필과 오늘의 미션 표시
```

성향 분석은 최초 분석과 사용자가 명시적으로 실행하는 재분석을 지원한다. 원본 답변은 이력으로 보존하고 현재 프로필은 최신 결과로 갱신한다. 동일 제출 키의 재요청은 중복 저장하지 않는다.

## 입력 항목

| 항목 | API 필드 | 의미 |
|---|---|---|
| 실내·실외 선호 | `indoorOutdoor` | 실내 선호에서 실외 선호까지, `-1..1` |
| 사회적 활동 선호 | `socialLevel` | 혼자 하기에서 함께하기까지, `-1..1` |
| 신체 활동 강도 | `physicalActivityLevel` | 정적인 활동에서 높은 움직임까지, `0..2` |
| 새로움 수용도 | `noveltyLevel` | 작은 변화에서 큰 변화까지, `0..2` |
| 실행 방식 | `executionStyle` | 계획형·유연형·즉흥형 |
| 관심 분야 | `interests` | 선택한 활동 카테고리 1~3개 |

성향 유형은 위 입력으로부터 결정적으로 계산되는 9개 유형 중 하나이며, 네 개 수치 축과 실행 방식·관심 분야를 함께 프로필에 저장한다. `energyLevel`과 `activityLevel`은 성향 API 입력으로 사용하지 않는다. 신체 활동 필드는 `physicalActivityLevel`로 구분한다.

## API 계약

### 성향 분석 제출

`POST /api/personality-analyses`

- 사용자 식별: `X-User-Key` Header
- 요청: 여섯 문항의 유효한 답변과 제출 식별 키
- 처리: 입력 검증 → 분석 → 원본 답변·관심 분야·현재 프로필의 원자적 저장
- 응답: 분석 버전, 유형, 네 축 점수, 실행 방식, 관심 분야와 분석 시각

### 사용자 프로필 조회

`GET /api/users/me`

현재 사용자와 성향 프로필의 존재 여부를 반환한다. 성향 분석이 완료되지 않은 사용자는 선택폼으로 이동하고, 완료된 사용자는 프로필과 오늘의 미션을 확인한다.

## 미션 추천 연계

- 네 축 점수는 미션과의 성향 거리 계산에 사용한다.
- 관심 분야는 사용자가 이미 익숙할 가능성이 있는 카테고리를 추천 후보에서 제외하는 데 사용한다.
- 실행 방식은 미션 `actionType`과의 적합도 점수로 사용한다.
- 난이도 적합도와 실행 방식 적합도는 미션 추천의 `contextFitScore`를 함께 구성한다.
- 미션 완료 후 갱신되는 성향은 `UserMissionService`가 처리하며, 이 문서의 최초 분석 저장 계약과 구분한다.

## 화면 계약

- 성향 선택 화면은 6개 질문을 단계적으로 표시하고 필수 입력을 검증한다.
- 선택지는 명사형 카테고리인 운동, 창작, 요리·미식, 학습, 교류, 야외활동, 정리·정돈, 문화생활을 사용한다.
- 분석 결과는 프로필 설명·점수·관심 분야·실행 방식과 함께 표시한다.
- 프로필 화면에서는 3D World를 오늘의 미션보다 먼저 표시한다.
- 재분석은 확인 팝업 후 실행하며, 팝업이 3D World 입력을 가리지 않도록 상호작용 영역을 분리한다.

## 저장 기준

원본 답변은 `SURVEY_RESPONSE`와 `SURVEY_INTEREST`, 현재 결과는 `USER_PERSONALITY_PROFILE`과 `USER_PROFILE_INTEREST`에 저장한다. 운영 스키마와 migration은 `supabase/migrations`를 기준으로 한다.

비밀번호와 사용자 키 원문은 저장하지 않으며, 인증은 계정 API와 `X-User-Key`를 사용한다. 실제 인증정보는 문서에 기록하지 않는다.

## 검증 기준

- 정상·필수값 누락·잘못된 enum·잘못된 사용자 키·중복 제출을 검증한다.
- `POST /api/personality-analyses`가 Swagger UI와 `/v3/api-docs`에 노출되는지 확인한다.
- 분석 결과를 저장한 뒤 `GET /api/users/me`와 Flutter 프로필에 동일한 값이 표시되는지 확인한다.
